# 流程图规则：先模块，后内部

README 里的流程图分**两层**，顺序固定：先讲"有哪些模块、各管什么"，再讲"每个模块里面怎么走"。

| 层 | 画什么 | 放在哪 | 数量 |
|---|---|---|---|
| **模块总览图** | 项目有哪几个模块、每个模块的**功能**是什么、模块之间怎么衔接 | 整个流程部分的**最前面** | 一张 |
| **模块内部流程图** | 该模块**内部**的步骤、判断分支、回路、需要用户确认的点 | 总览之后，每个模块一节，图在前、介绍在后 | 每个模块一张，复杂的可以多张 |

总览图里的模块和后面的内部流程图**一一对应**，用同一个名字。读者先在总览图里看到"计划盘点"这一块，往下翻就能找到"计划盘点"的内部流程。

## 什么是"模块"

- **技能包**：一个 Skill 就是一个模块；有子 Skill 的，子 Skill 作为所属模块的内部步骤或单独的小模块，不要和主模块并列堆在总览图里。
- **工具/应用**：用户能感知到的一项主要功能。
- **网站/产品**：一个核心功能页或一条核心使用路径。
- **库/SDK**：以调用链路为主，通常只需要一层内部流程，总览图可以省略。

只有一个模块的项目，只画内部流程一层，不要硬凑总览。

## 总览图怎么画

- 回答的是"这个项目由哪几块组成、各自做什么"：每个模块一个块，块上写模块名，下方一句话写**它的功能**；块之间用箭头表示先后或数据流向。
- **不画内部步骤。** 内部的分支、回路、判断留给后面的内部流程图；总览里出现"如果……就……"，说明画深了。
- 元素控制在 8 个以内；模块超过 6 个时，先按用途分组（例如"收集""投递"），再各画各的总览，不要塞进一张。
- 每个模块的功能描述必须出自该模块的 SKILL.md、源码或文档，不凭印象写。

## 内部流程图怎么画

- 只讲这一个模块：入口、主线步骤、判断分支、回到前面的回路、需要用户拍板的点、出口交给谁。
- 判断和需要用户确认的地方要在图上明显标出，不要藏在文字里。
- 每张图后面跟一段介绍：先说这个模块做什么，再按图里的顺序讲，把分支和"你要做的决定"说清楚；介绍里的每个说法都能在图里或项目里找到对应。
- 同一模块的步骤太多放不下，拆成"主线图 + 某个关键环节的细节图"，不要把图画成一屏看不完。

## 顺序和命名

README 里的顺序：**总览图 → 模块一的内部图与介绍 → 模块二的内部图与介绍 → ……**。图的标题用"模块名 + 内部流程"，总览图的标题用"项目名 + 模块与功能"。图和介绍里不要出现"阶段"和"模块"混用的叫法，选一个词用到底。

## 风格与工具

- 全部流程图**同一种风格**，不要在一个 README 里混用不同的绘图风格。推荐用 `excalidraw-flowchart` Skill 画：总览图用手工构图，内部流程图用流程规格自动排版，画出来是同一种手绘白板风。
- 不用的话，也必须做到：同一份 README 里字体、配色、箭头样式一致；判断块、终止块、回路的画法一致。

## 门禁与自检

- 框架确认（门禁①）时，把"模块与流程"这一节拆成"总览 + 每个模块各一节"的清单一起给用户确认；逐节迭代（门禁②）时，**先定总览，再逐个模块**。
- 每张图都要用事实核对表登记：图里每个节点、每个分支是否有项目内证据；无证据的不画。
- 图画完必须**实际看一遍成图**：文字有没有被切掉或压在线上、箭头有没有指错、分支标签对不对得上、总览里的模块和后面的内部图是否一一对应。没看过的图不交给用户。
- 图里不画项目做不到的能力，也不画与"边界"声明矛盾的步骤（例如边界写"不替你提交"，图上就不能出现自动提交）。
